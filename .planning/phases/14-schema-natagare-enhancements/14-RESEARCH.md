# Phase 14: Schema & Natagare Enhancements - Research

**Researched:** 2026-02-05
**Domain:** Prisma schema migration, Swedish natagare tariff configuration, peak billing timing
**Confidence:** HIGH

## Summary

Phase 14 extends the existing Natagare model with two new capabilities: (1) overforingsavgift (transfer fee) in ore/kWh, and (2) configurable effect tariff timing for high-load hours with summer/winter seasonality. The research confirms that Swedish grid operators use varying tariff structures, with Ellevio using 7 ore/kWh transfer fee and 22:00-06:00 night discount, while other operators like Jonkoping Energi use weekday 07:00-20:00 November-March as high-load periods.

The technical implementation follows the established expand-and-contract migration pattern already used in Phase 8/9. The Natagare model already has `peakNightStartHour/peakNightEndHour` fields - this phase adds `overforingsavgiftOreKwh`, `highLoadStartHour/highLoadEndHour`, and `isWinterOnlyHighLoad` for seasonal distinction. The existing `NatagareEditForm` component provides the UI pattern to extend.

**Primary recommendation:** Add nullable fields with sensible defaults (7 ore/kWh for overforingsavgift, 07:00-20:00 for high-load), backfill existing records in migration SQL, and extend the existing natagare edit form with new configuration sections.

### Pattern 1: Nullable Field with Default Backfill
**What:** Add new columns as nullable with Prisma @default, backfill in migration SQL
**When to use:** Extending existing models with data
**Example:**
```prisma
// prisma/schema.prisma
model Natagare {
  // Existing fields...

  // NEW: Phase 14 - Transfer fee and tariff timing
  overforingsavgiftOreKwh Decimal? @db.Decimal(10, 2) @default(7.00)

  // High-load hours for effect tariff (distinct from night discount hours)
  highLoadStartHour Int? @default(7)   // Default 07:00
  highLoadEndHour   Int? @default(20)  // Default 20:00

  // Seasonal flag: true = high-load only applies Nov-Mar (winter)
  isWinterOnlyHighLoad Boolean @default(false)
}
```

### Pattern 2: Migration with Backfill
**What:** Create migration with --create-only, add UPDATE statements manually
**When to use:** Adding fields to tables with existing records
**Example:**
```sql

  "overforingsavgiftOreKwh" = 7.00,
  "highLoadStartHour" = 7,
  "highLoadEndHour" = 20,

```

## Common Pitfalls

### Pitfall 1: Inconsistent Tariff Timing Fields
**What goes wrong:** Multiple time window fields (dayStartHour, peakNightStartHour, highLoadStartHour) confuse implementers
**Why it happens:** Organic schema growth without clear documentation
**How to avoid:** Document the three distinct time window concepts:
- `dayStartHour/dayEndHour`: Basic day/night tariff split (for nightRateSekKw)
- `peakNightStartHour/peakNightEndHour`: Night discount for peak calculations (50% discount)
- `highLoadStartHour/highLoadEndHour`: High-load period (NATA-13 requirement - distinct timing)
**Warning signs:** Developers confuse which fields to use for which calculation

### Pitfall 2: Overforingsavgift Unit Confusion
**What goes wrong:** Mixing ore/kWh with SEK/kWh in calculations
**Why it happens:** Swedish pricing uses ore (100 ore = 1 SEK), but codebase has both units
**How to avoid:**
- Field name explicitly includes unit: `overforingsavgiftOreKwh`
- Add conversion constant in constants.ts: `ORE_PER_SEK = 100`
- Document unit in Prisma schema comment
**Warning signs:** Savings calculations 100x too high or too low

### Pitfall 3: Winter-Only Logic Breaking Year-Round Calculations
**What goes wrong:** Calculations during summer months return unexpected results
**Why it happens:** `isWinterOnlyHighLoad = true` but code doesn't handle summer fallback
**How to avoid:** When `isWinterOnlyHighLoad = true`:
- Nov-Mar (months 10, 11, 0, 1, 2): Use high-load hours
- Apr-Oct: Fall back to full-day or no high-load distinction
**Warning signs:** Zero savings calculated in summer months

### Pitfall 4: Form Not Showing New Fields Until Page Refresh
**What goes wrong:** Super Admin saves natagare but new fields don't appear
**Why it happens:** React state initialized from old props, router.refresh() not triggering
**How to avoid:** Use key={natagare.id} on form component to force remount on selection change
**Warning signs:** Old values persist after navigating between natagare in config panel

### Pitfall 5: Missing Type Updates for Peak Billing
**What goes wrong:** TypeScript errors when consuming new natagare fields in peak-billing code
**Why it happens:** PeakMethodConfig type not updated to include new timing fields
**How to avoid:** Update types.ts PeakMethodConfig interface with new optional fields
**Warning signs:** Type errors in calculatePeakBilling after schema changes

### Season Check Utility
```typescript
// src/lib/calculations/peak-billing/season.ts - new file
// Source: Phase 14 requirement NATA-14

/**
 * Check if a month is in winter season (Nov-Mar).
 * Used for isWinterOnlyHighLoad natagare configuration.
 * @param month 0-indexed month (0 = January, 11 = December)
 */
export function isWinterMonth(month: number): boolean {
  // Winter: November (10), December (11), January (0), February (1), March (2)
  return month >= 10 || month <= 2
}

/**
 * Check if an hour is within high-load period.
 * Respects winter-only flag if configured.
 */
export function isHighLoadHour(
  hour: number,
  month: number,
  config: {
    highLoadStartHour?: number
    highLoadEndHour?: number
    isWinterOnlyHighLoad?: boolean
  }
): boolean {
  const { highLoadStartHour = 7, highLoadEndHour = 20, isWinterOnlyHighLoad = false } = config

  // If winter-only and not winter, no high-load
  if (isWinterOnlyHighLoad && !isWinterMonth(month)) {
    return false
  }

  // Simple range check (no overnight wrap for high-load)
  return hour >= highLoadStartHour && hour < highLoadEndHour
}
```

## Open Questions

Things that couldn't be fully resolved:

1. **Exact overforingsavgift for Vattenfall and E.ON**
   - What we know: Ellevio = 7 ore/kWh (verified from official website)
   - What's unclear: Vattenfall and E.ON specific rates (PDF not parseable)
   - Recommendation: Use 7 ore/kWh as default, Super Admin can configure actual values

2. **Whether high-load applies to weekends**
   - What we know: Jonkoping Energi specifies "weekdays" (vardagar)
   - What's unclear: Whether to add a boolean `excludeWeekendsHighLoad` field
   - Recommendation: Defer weekend logic; most residential billing is monthly average anyway. Add field in future phase if needed.

3. **Interaction between night discount and high-load**
   - What we know: Night discount (50% reduction) and high-load are conceptually separate
   - What's unclear: If any natagare combines both (discount during non-high-load hours)
   - Recommendation: Keep fields separate, let peak calculation logic combine them appropriately
